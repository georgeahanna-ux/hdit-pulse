How Pulse is run

  • One sign-in. Everyone signs in with Microsoft 365 (Entra ID). What they can see comes only from their Pulse groups. There are no Pulse passwords.
  • Least privilege. Each part of Pulse can reach only what it needs. The user-facing API can't read integration credentials; the sync service can. Each Pulse module may do only the Autotask actions on its allow-list (section 6).
  • Credentials are write-only. They're entered on the Connections page or into Key Vault, never shown again, never logged, never stored in the database and never sent to the browser. Nobody, including Claude, needs to see them.
  • Everything is audited. Sign-ins, changes, overrides, setting changes and views of sensitive pages go to the audit log, which can't be edited (section 14).
  • Every change is a release. Code, settings in code and infrastructure change only through GitHub, with a version number and release notes, tested in the test environment first (section 16). This is the change record for ISO 9001 and ISO 27001.
  • Platform Admins: George Hanna and Bernadette Hanna. Keep it to two or three people: the role is administrator in Pulse and in every app.

People directory and Autotask links

Platform → People and departments. Pulse links each person (by their Entra object id) to their Autotask resource by matching every one of their Microsoft 365 addresses against active Autotask resources' email fields. Exactly one match links automatically. Anything else goes to Needs review.

  • Fix or Change link sets the right Autotask resource, or "No Autotask account" (for example external providers). Needs a reason; audited. A Platform Admin's link overrides matching.
  • The link decides "My clients", "My tasks", time entries and whose name Autotask changes are made under. Someone with no link can still use Pulse but can't log time.
  • Entra is read nightly (02:40 Sydney in summer) and Autotask every 15 minutes. Refresh reads them now.
  • Autotask departments: Leadership and Platform Admins can change people's default department (written to Autotask, audited). A tech is anyone whose default department is Service Desk; that drives tickets per tech and utilisation on the Scorecard.

The Autotask API user

Pulse, Pipeline, Marketing ROI and Whitespace all use one Autotask API user (Key Vault secret autotask-service). Least privilege is enforced in two layers: its Autotask security level, and each Pulse module's allow-list in code (lib/autotask.js), which refuses anything not listed before a request leaves Pulse. No module can delete records, apart from removing a task dependency link.

Teams app, reminders and the Monday email

Installing the Teams app

  1. Connections → Microsoft Teams and email → Download the Teams app (a zip built for this environment with each release).
  2. Teams admin centre → Teams apps → Manage apps → Upload new app, and choose the zip. For a new version, open the app and upload the file again.
  3. Teams apps → Setup policies → Global (or a policy for staff) → add Pulse to Installed apps and Pinned apps, so it's in everyone's app bar.
  4. In the leadership team's channel: + (Add a tab) → Pulse → choose the L10 page.

Teams signs people in to Pulse. That needs bash pulse-setup.sh release1-entra to have been run (it adds Pulse's Teams identifier and pre-approves Teams and Microsoft 365 as clients).

Reminders

Sent to each person's Teams Activity feed by the nudges job (every 15 minutes), once each: Monday numbers to enter (8am) and off-track Rocks (9am); Tuesday L10 (9am); new To-dos after an L10; overdue To-dos (weekdays, working hours); and, for Account Managers, a client moving into At risk. They need the sync identity's Graph permission TeamsActivity.Send and the person to have the Pulse app installed. Each person can switch them off under Notifications. Pause all reminders on Connections stops them for everyone (audited).

The Monday email

At 7am Monday to people who have signed in within 90 days, from the shared mailbox set on Connections. Exchange Online "RBAC for Applications" lets the sync identity send from that one mailbox only (no Graph Mail.Send in Entra). Set up with ./pulse-mail.ps1 in Cloud Shell PowerShell (section 15). A new permission can take up to an hour to apply.

Azure OpenAI and ticket sentiment

Client health reads how clients sound in their own tickets with Pulse's own Azure OpenAI resource.

  • Where: a Regional Standard deployment of gpt-4.1-mini (2025-04-14) in Australia East, so text is processed in Australia (decided 12 Nov 2026). No Global or Data Zone deployment. Keys are off; only the sync identity (role "Cognitive Services OpenAI User") can call it. Outbound calls from the resource are blocked; audit logs go to Log Analytics.
  • What is sent: for tickets clients raised (not alerts or monitoring), created in the last 30 days or still open: the title, the description and notes that aren't internal, marked Client or HD IT. Email addresses, phone numbers, long numbers, links with query strings and quoted email history are removed first.
  • What is kept: per ticket, the sentiment, frustration (0–3), whether it talks about leaving, a one-line reason (names and contact details stripped) and a fingerprint (SHA-256) of the text sent, so it's read again only when it changes. Never the ticket text. Kept 120 days.
  • Microsoft: doesn't use the data to train models. Its abuse monitoring may keep prompts for up to 30 days; HD IT can apply to Microsoft for modified abuse monitoring. Record Azure OpenAI in the supplier and data-flow register.
  • Switching off: Client health → How the Early Warning score works → Switch off (Platform Admins, with a reason, audited). The next hourly run sends nothing.
  • Cost: about 300,000 tokens per 400 tickets, a few cents. After the first catch-up only new or changed tickets are read.
  • Model retirement: Microsoft retires gpt-4.1-mini on Azure on 14 April 2027. Before then, either deploy a newer model offered as Regional Standard in Australia East (a change to infra/openai.bicep, as a release) or decide again on the region.

Scorecard and FY plan administration

  • On trial to automatic: each automatic measurable starts on trial. When its automatic values match what owners type in, Leadership switches it to automatic from the measurable's panel, with a reason. Switch back the same way.
  • Locking: a week locks at 5pm on the Tuesday after it ends; after that, changes are overrides with a reason.
  • Definitions (what a seat, tech, MRR, SGM are) are in the requirements (D4) and each measurable's panel. Seat services, the tech department, hours per day and Xero account lists are settings (section 12).
  • FY plan: Leadership sets year targets and opening levels; Leadership and Finance set quarter targets and month-end figures. Automatic MRR, seats and new seats are on trial until switched on.

Client health administration

  • Clients are companies with a recurring contract in force. HD IT's own company (Autotask company 0) is never a client.
  • Account Manager is the company's owner in Autotask. To move a client to another Account Manager, change the owner in Autotask; Pulse follows at the next nightly run.
  • Feedback is matched to a client by the Autotask ticket SimpleSAT holds, then the contact, then the company name. Diagnose shows how many ratings weren't matched.
  • Score weights are in code (clients/model.js) and listed on the page under How the Early Warning score works. Changing them is a release. Review them after a few weeks of real data, especially "tickets open more than 14 days", which fires for many clients.
  • At-risk alerts go to the Account Manager once a week per client, and not on the first run after a reset.
  • Who sees it: Leadership, Sales & Marketing and Managed Services. MRR only for Leadership and Sales & Marketing. Opening a client is audited (the page shows client contacts' names and comments).

Audit log and access review

  • Platform → Audit log (Platform Admins and Compliance): filter by person, action and date range. Each entry has who, when, before and after, and the reason.
  • Views of sensitive pages are recorded: finance detail, People data, the audit log, Connections, and each client opened in Client health.
  • Quarterly access review (ISO 27001): Compliance exports group membership from Entra for every Pulse group (Pulse doesn't export it itself yet) and confirms each person still needs it; Platform Admins remove anyone who doesn't. Keep the export and sign-off as the record.

Releases and change control

  • Every change is a commit to the Pulse GitHub repository with a version number (major.minor.patch) and an entry in What's new and CHANGELOG.md.
  • Each release updates the user guide, this admin guide and What's new. The build stops if any of them, or the app, carries a different version.
  • Pushing to main tests and deploys to test: backend tests, infrastructure (Bicep), database migrations, both Function Apps, the website and the Teams app package. A failed test stops the deploy.
  • Production (from 1.0.0) deploys only from a GitHub release approved by a Platform Admin, after it has run in test.
  • The requirements, architecture and identity documents (docs/, also in the claude.ai project) record each decision with its date.
17

Diagnose

In GitHub: Actions → Diagnose test → Run workflow. It signs in as the deploy identity and prints, without any credential values: the last sync runs and failures, which credentials are entered, refresh requests, counts of Autotask data in Pulse, the latest automatic values, link status, Client health counts, ticket sentiment counts and the last reminders. Optional inputs:

  • refresh_job: run a job now (scorecard, projects, departments, directory, connections, links, nudges, clients, sentiment). Run Diagnose again a few minutes later to see the result.
  • inspect:simplesat or inspect:simplesat-responses: SimpleSAT's field names (no customer details).
  • inspect_opportunity: one Autotask opportunity and its quotes, read-only.

Backup, restore and recovery

  • Database: Azure SQL keeps automatic backups with point-in-time restore: 7 days on Basic (test), up to 35 days on S0 (production). Restore to a new database in the Azure portal (SQL database → Restore), check it, then point Pulse at it by a release. Consider monthly long-term backups kept 12 months for ISO.
  • Credentials: Key Vault soft delete keeps deleted secrets for 90 days (Key Vault → Secrets → Manage deleted secrets → Recover).
  • Everything else is rebuilt from GitHub: re-running the deploy recreates the website, Function Apps, Azure OpenAI and settings from code.
  • If a release breaks something, deploy the previous version's commit (revert it in GitHub); database migrations add tables and columns rather than removing them, so the earlier code still runs against the newer database.

Before production (1.0.0)

  • Repeat the setup steps in HD IT's main tenant with production names.
  • Conditional Access on the HD IT Pulse enterprise app: MFA and a compliant device.
  • Microsoft Defender for Cloud on SQL and the Function Apps; 12-month log retention; Key Vault purge protection.
  • The production deploy workflow with a Platform Admin's approval.
  • pulse.hdit.com.au on the website, added as a redirect address on the app registration.
  • Turn off the apps' team passwords (LEGACY_PASSWORD_LOGIN) once their people use Pulse.
  • Supplier and data-flow register: Azure, Azure OpenAI, SimpleSAT, Xero, Autotask.
